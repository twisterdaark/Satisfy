# Satisfy — قواعد التشغيل بين حسابَي Claude

> الحالة: مقترح للمراجعة (PR). يسري بعد الدمج في `main`، ويُعمل به مؤقتًا من لحظة فتح الـPR.
> المالك البشري وصاحب القرار النهائي: `@twisterdaark`.

## 1. مصدر الحقيقة

- السجل المشترك الوحيد هو GitHub: Issues وPRs وCommits.
- كلام أي جلسة (محادثة، ملخص، ذاكرة) **ليس إثباتًا**. الإثبات = Commit SHA أو Issue/PR أو تعليق موقّع عليها.
- قبل بدء أي مهمة: اقرأ أحدث Issues وPRs المفتوحة و`main`، وتأكد أن العمل غير منفذ أو محجوز.
- لا تُنشأ Issue جديدة إذا كانت هناك Issue قائمة تعالج نفس العمل؛ أضف تعليقًا عليها.

## 2. الهويات والتوقيع

قد يكتب الحسابان باسم مستخدم GitHub واحد، لذلك **كل أثر يجب أن يحمل توقيعًا**:

| الأثر | التوقيع |
|---|---|
| تعليق على Issue/PR | السطر الأول: `[Claude-A] <TYPE> <TASK-ID>` أو `[Claude-B] ...` |
| عنوان PR | يبدأ بـ `[Claude-A]` أو `[Claude-B]` ثم معرّف المهمة |
| الفرع | `claude-a/<task-id>-<slug>` أو `claude-b/<task-id>-<slug>` |
| Commit | السطر الأخير قبل الـtrailers: `Agent: Claude-A` أو `Agent: Claude-B` |

تعليق غير موقّع لا يُحتسب ACK ولا مراجعة.

## 3. الأدوار

- **Claude-A** — Core Architecture وOnline Multiplayer، والمنسق والمكامل: يوزع المهام، يراجع ويدمج PRs.
- **Claude-B** — المحتوى: الوحوش، المهام، الوصفات، المناطق، الكلاسات، المهن، المودة، السمعة، واختبارات المحتوى والتوازن، ومراجعة PRs الهندسية لـClaude-A.

## 4. المهام

- معرّف المهمة: `SAT-<AREA>-NNN` (مثل `SAT-ONLINE-001`, `SAT-CONTENT-001`). المعرّف في عنوان الـIssue.
- **مالك واحد** لكل مهمة، يظهر في الـlabel `owner:claude-a` أو `owner:claude-b` وفي جسم الـIssue.
- جسم كل Issue يحتوي: المالك، المهمة، الملفات المسموحة، الملفات الممنوعة، Dependencies، الاختبارات، الفرع، الحالة.
- دورة الحالة (labels):
  `status:assigned` → `status:acked` → `status:in-progress` → `status:in-review` → `status:done`
  و`status:blocked` عند التوقف.
- النطاق **لا يُعتبر محجوزًا** للمالك إلا بعد `ACK` موقّع منه.

## 5. أنواع الرسائل

تُكتب كتعليقات على الـIssue أو الـPR. السطر الأول ثابت الصيغة حتى يمكن البحث عنه.

```
[Claude-A] ASSIGN SAT-XXX-NNN → Claude-B
النطاق: ... | الفرع: ... | المطلوب للـACK: قراءة الـIssue والرد بـACK
```

```
[Claude-B] ACK SAT-XXX-NNN
فهمت النطاق والملفات الممنوعة. الفرع: claude-b/sat-xxx-nnn-slug
```

| النوع | متى |
|---|---|
| `ASSIGN` | المنسق يسند مهمة لمالك |
| `ACK` | المالك يقبل النطاق؛ يبدأ الحجز من هنا |
| `STATUS` | تقدم: الفرع، آخر Commit، ما تم، ما تبقى |
| `BLOCKED` | توقف بسبب Dependency أو قرار بشري |
| `REVIEW_REQUEST` | الـPR جاهز للمراجعة المستقلة |
| `REVIEW: APPROVE` / `REVIEW: CHANGES_REQUESTED` | نتيجة المراجعة، مع الاختبارات التي نُفذت ونتائجها |
| `SCOPE_CONFLICT` | تعارض في ملف أو مسؤولية؛ يوقف العمل في الجزء المشترك |
| `HANDOFF` | نقل ملكية ملف/وحدة بشكل صريح |
| `DONE` | المهمة دُمجت وأُغلقت |

## 6. ملكية الملفات — المرحلة 1 (قبل تقسيم المحرك)

| المسار | المالك | ملاحظة |
|---|---|---|
| `index.html` | **Claude-A فقط** | ممنوع على Claude-B تعديله بالتوازي |
| `src/core/**`, `src/net/**`, `src/world/**` | Claude-A | المحرك، الحالة، الحفظ، الأونلاين |
| `tests/regression/**`, `tests/unit/**`, `tests/harness/**` | Claude-A | |
| `docs/architecture/**`, `docs/api/**`, `docs/coordination/**` | Claude-A | Claude-B يقترح تعديلات عبر Issue/PR review |
| `package.json`, `.github/**` | Claude-A | Claude-B يطلب أي سكربت اختبار يحتاجه |
| `data/**` | Claude-B | بيانات محتوى خالصة بلا منطق |
| `tests/content/**` | Claude-B | اختبارات المحتوى والتوازن |
| `docs/content/**` | Claude-B | مخططات ووثائق المحتوى |
| `README.md` | Claude-A | تغييرات بسيطة فقط بعد موافقة المالك البشري |

- بعد دمج تقسيم المحرك، يُسجَّل `HANDOFF` يمنح Claude-B ملكية وحدات المحتوى المنفصلة، ويُحدَّث هذا الجدول في PR.
- أي ملف غير مذكور: يُطلب حجزه في الـIssue قبل تعديله.

## 7. الفروع والدفع

- ممنوع: Push مباشر إلى `main`، Force Push على فرع ليس لك، أي تعديل على فرع الحساب الآخر.
- مسموح: Rebase/Force-with-lease على فرعك فقط.
- كل عمل = فرع + PR يشير إلى الـIssue (`Refs #N` أو `Closes #N`).

## 8. المراجعة والدمج

لا يُدمج PR إلا إذا تحققت كل الشروط:

1. مراجعة مستقلة من **الحساب الآخر** بتعليق `REVIEW: APPROVE` موقّع (GitHub لا يسمح بموافقة رسمية من نفس المستخدم، لذا التعليق الموقّع هو المعتمد).
2. `npm test` ناجح، مع ذكر النتيجة في المراجعة.
3. لا يوجد `SCOPE_CONFLICT` مفتوح على نفس الملفات.
4. الـPR لا يغير Gameplay إلا إذا نصت الـIssue على ذلك صراحة.

الدمج ينفذه Claude-A (المكامل). إن كان الـPR لـClaude-A نفسه فلا يُدمج قبل `REVIEW: APPROVE` من Claude-B.

## 9. التعارض

1. من يكتشف التعارض يكتب `SCOPE_CONFLICT` على الـIssue المعنية، ويذكر الملفات والـCommits.
2. يتوقف الطرفان عن العمل في الجزء المشترك فقط.
3. Claude-A يحسم الملكية بتعليق `HANDOFF` أو بتعديل الـIssue؛ وإن تعذر الحسم يُرفع للمالك البشري.

## 10. حدود الأمان

- لا Credentials أو مفاتيح أو أسرار في المستودع أو التعليقات.
- لا إنشاء حسابات خارجية ولا تفعيل خدمات مدفوعة (مثل Firebase Blaze) دون موافقة المالك البشري مسجلة في Issue.
- اللعب Offline يجب أن يبقى يعمل دائمًا دون تسجيل دخول.
- لا PvP مفتوح قبل Server Authority.

## 11. نهاية كل جلسة

تعليق `STATUS` على كل Issue عمل عليها الحساب: الفرع، آخر Commit SHA، الـPR، ما نُفذ، نتائج الاختبارات، الخطوة التالية.
