# Content data schema (SAT-CONTENT-001)

Owner: Claude-B. Consumer: Claude-A, who writes the loader and the condition evaluator.

Status: parity extraction only. Nothing in `index.html` reads these files yet.

## Files

Every file is a classic script. It works from `file://`, from GitHub Pages and from Node `vm`, and it adds one key to `window.SATISFY_DATA` (or `globalThis.SATISFY_DATA` in Node).

| File | Key | Source tables in `index.html` | Records |
|---|---|---|---|
| `data/monsters.js` | `monsters` | `MT`, `BOSSES`, `SPAWN` | `types` (16), `bosses` (4), `spawns` (14) |
| `data/quests.js` | `quests` | `QD`, static entries only | `quests` (22) |
| `data/recipes.js` | `recipes` | `RC` | `recipes` (12) |
| `data/skills.js` | `skills` | `SKD`, `TLS` | `skills` (14), `titleSkills` (3) |
| `data/npcs.js` | `npcs` | `NPCS`, `NPCS.push`, `NPCT` | `npcs` (16: 11 outdoor, 5 interior) |
| `data/zones.js` | `zones` | `TOWNS`, `ZR`, `ZL`, world constants | `towns` (2), `regions` (13), `labels` (14) |
| `data/classes.js` | `classes` | `QD` entries with `cls`, plus `SKD` | `classes` (5, including `novice`) |

The files are generated by `node data/tools/build-data.cjs`, which reads `index.html` and does not modify it. Until the content handoff, `index.html` is the source of truth. `tests/content/data.test.cjs` fails if any file drifts from it.

## Common fields

- File header: `schema` (currently 1), `src`, `sourceFile`, `sourceVersion` (the `main` SHA the data was read from) and `tables`.
- Every record has a stable `id` and `src: "PER_CODE"`. Keyed tables also use the `id` as the key. Lists such as spawns and regions carry their own `id`.
- Values are JSON-only. There are no functions, no `undefined` and no randomness.
- Field names and value shapes are the same as in `index.html`. Examples: `lv: [min, max]`, `drop: [[material, chance]]`, and quest `obj: {t, it, n, take}`. This keeps the loader a straight mapping.
- These fields are added on top of the source:
  - `id` and `src` on every record.
  - Declarative conditions: `unlock` on recipes and skills, and `offer` on quests.
  - `_srcFn` with the original source text, next to every value that was converted from a function.
  - In `npcs.js`: `interior`, `room` and `dialog`.
  - In `monsters.js`: spawn and boss records become objects instead of tuples.

## Conditions

A condition is an object with exactly one operator. The evaluator gets the player state `S`, which is the same object the game uses today.

| Operator | Value | True when | Source equivalent |
|---|---|---|---|
| `all` | list of conditions | every one is true | `a && b` |
| `any` | list of conditions | at least one is true | `a \|\| b` |
| `not` | one condition | it is false | `!a` |
| `questTaken` | quest id | the quest was accepted at some point (any state) | `!!S.qs.id` |
| `questDone` | quest id | the quest is finished | `qDone(id)`, i.e. `S.qs[id].st === 2` |
| `lv` | `{gte: n}` | player level ≥ n | `S.lv >= n` |
| `smithLv` | `{gte: n}` | smithing level ≥ n | `S.smith >= n` |
| `cls` | class id | the current class equals it | `S.cls === id` |
| `title` | title id | the equipped title equals it | `S.title === id` |
| `classQuestActive` | `true` | some class quest (one with `cls`) is in progress | `Object.keys(S.qs).some(k => QD[k].cls && S.qs[k].st === 1)` |

A reference evaluator, about 10 lines, is in `tests/content/data.test.cjs`. The test runs every recipe's source function and its condition against the same sample states and checks that they agree.

### Where conditions appear

- **`recipes[*].unlock`** is converted from `RC[*].unlock`. Every conversion has its `_srcFn`.
- **`skills[*].unlock`** comes from `skOK`. A title skill becomes `{title}`, and every other skill becomes `{lv: {gte}}`. The class filter is a separate field, `cls`, where `any` means every class, the same as `clsSkills()`.
- **`quests[*].offer`** is the rule for when a giver offers the quest: `qAvail(id) && S.lv >= (lv || 1)`, used by `npcMark`, `trLine` and the board. It lists, in order:
  1. not taken,
  2. `pre` done,
  3. `cl2` class,
  4. for class quests, `cls: novice` and no other class quest active,
  5. the level.

  The raw `pre`, `cl2`, `cls` and `lv` fields are still there, so the loader can keep calling the existing functions if it prefers.

## Per-file notes

- **monsters**:
  - Spawn ids are `<type>-<n>`, numbered in source order within each type. A spawn rect is `x0..x1, y0..y1` in tiles, and `n` is the number of monsters.
  - Boss ids are the monster type, because each boss appears once.
- **quests**:
  - Board quests generated at runtime (`gen: 1`, from `regBQ`) are not content and are left out.
  - The objective type `visit` has one target today, `grave`, which is handled by `visitGrave()`.
- **npcs**:
  - Interior NPCs have `room: {bi, dx, dy}` instead of `tx`/`ty`. `bi` is the building index. The engine resolves it with `rmP(bi, dx, dy)` against `ROOMS`, which is built at load time.
  - `dialog` copies `NPCT`. A constant line key stays a string. A function that returns one constant becomes `{key, _srcFn}`. Logic such as random lines, shop options and the raid offer stays as `{_srcFn}` text, for Claude-A to port. It is listed here so nothing is lost.
- **zones**:
  - `regions` keep the `ZR` order, because zone lookup is first match. For example, `zQuarry` lies inside `zBai`. `order` makes that explicit.
  - Outside every region the zone is `fallback` (`zPlains`).
  - Inside a house the zone comes from the building (`room.z`).
  - `world` holds `TS, MW, MH, WH, BW, WMH`.
- **classes**:
  - This file is derived and has no table of its own in the code. Each class comes from its class quest: `quest`, `trainer` (the giver), `lv`, `pre` and `item`.
  - Its `skills` come from `SKD` entries with that `cls`.
  - `sharedSkills` holds the `cls: 'any'` skills (`strike`).

## Out of scope here

These are left out on purpose: string tables (`STR`), shop prices inside dialogue logic, weapon sprites (`WSH`), items and drops beyond materials, and any new novel content. Expansion proposals go to a separate `SAT-CONTENT-002` STATUS.
